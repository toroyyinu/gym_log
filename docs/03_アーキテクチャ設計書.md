## 1. 方針

| 方針 | 理由 |
|---|---|
| **サーバーを持たない**（静的ファイルだけで動く） | 無料で運用でき、記録を外部に送らない（プライバシー） |
| **データは端末内の IndexedDB に保存する** | localStorage より容量に余裕があり、検索用のインデックスを作れる |
| **フレームワークもビルドも使わない**（HTML・CSS・素の JavaScript、ES Modules） | 自分で読んで改造しやすい。ファイルを保存すればすぐ動作を確認できる |
| **表示（HTML）と処理（JavaScript）を別のファイルに書く** | 読みやすくするため。画面の見た目は HTML ファイルを、動きは JS ファイルを見れば分かるようにする（「7. 画面描画とスタイル」） |
| **外部ライブラリを読み込まない** | 外部への通信をなくし、オフラインでも確実に動かす。グラフは SVG で自作する |
| **PWA にする**（Web App Manifest＋Service Worker） | ホーム画面から起動でき、オフラインで動く。ホーム画面に追加するとデータも消えにくくなる（PRD「6. 前提・制約」を参照） |

## 2. 全体構成

```
┌──────────── iPhone ────────────┐
│ ホーム画面のアイコン               │
│   ↓ 起動                          │
│ ┌──── Webアプリ（頑張れジム通い）────┐ │
│ │ 画面（HTML/CSS/JS）            │ │
│ │   ↕                            │ │
│ │ データ層 db.js ↔ IndexedDB ◀── 記録データはここだけ
│ │                                │ │
│ │ Service Worker（アプリ本体のキャッシュ）│
│ └───────────────────────┘ │
└──────────────────────────┘
          ▲ 初回と更新時だけ、アプリ本体（コード）を取得する
          │（記録データは送らない）
   GitHub Pages（HTTPS で静的ファイルを配信）
          ▲ git push
   Mac（開発・CSV分析）
```

- iPhone と GitHub Pages の間で通信するのは、**アプリ本体のファイル** だけ。
- 記録データは IndexedDB の中だけにある。PC に移すのは、ユーザーが書き出したファイルを AirDrop などで送ったときだけ。

### モジュールの依存関係

```
main.js ──▶ views/*.js, record-editor.js, banners.js, pwa.js, seed.js, db.js, ui.js

views/*.js ──▶ db.js ──▶ IndexedDB
     │          └─▶ domain.js（lastPerformed だけ）
     ├──▶ domain.js（計算・入力チェック）
     ├──▶ ui.js ──▶ domain.js
     ├──▶ record-editor.js ──▶ db.js, domain.js, ui.js（record・history・graph）
     ├──▶ banners.js ──▶ db.js, domain.js, pwa.js, ui.js（record・settings）
     ├──▶ chart.js（graph だけ。データ層には触らない）
     ├──▶ io.js ──▶ domain.js（settings だけ）
     └──▶ pwa.js、seed.js（settings だけ）
```

- 画面（views）は IndexedDB を直接触らず、必ず `db.js` を通す。保存先を将来変えるときに、`db.js` だけを直せば済むようにするため。
- 計算のルールは `domain.js` にまとめ、画面やデータベースに触らない関数だけを置く。`tests/` からそのまま確かめられるようにするため。

## 4. 画面の切り替え（ルーティング）

URL の `#` 以降で画面を切り替える（ハッシュルーティング）。

| URL | 画面 |
|---|---|
| `#/record` | S-1 記録（初期画面） |
| `#/history` | S-3 履歴 |
| `#/graph` | S-5 グラフ |
| `#/settings` | S-6 設定 |
| `#/exercise/new` | S-7 種目編集（新規）。`?from=record` がつくと、保存後にその種目を選んだ状態で S-1 に戻る |
| `#/exercise/<id>` | S-7 種目編集（既存） |

- S-2・S-4 は、URL を変えずにシート（下からせり上がる画面）として開く。画面を切り替えたときは閉じる。
- ハッシュ方式にすると、GitHub Pages で URL の設定をしなくても、再読み込みで 404 になることを避けられる。

## 5. データ層

### 5.1 IndexedDB の構成

データベース名：`gym_log`　バージョン（`DB_VERSION`）：`1`

| ストア | キー | インデックス | 内容 |
|---|---|---|---|
| `exercises` | `id` | `name`（重複不可） | 種目 |
| `muscles` | `id` | `group` | 筋肉 |
| `records` | `id` | `exerciseId`、`performedAt`、`[exerciseId, performedAt]` | 記録（筋トレは1セット、有酸素は1回） |
| `meta` | `key` | — | 設定値（下の表） |

各項目の意味は、機能設計書「5. データ項目定義」のとおり。

**設定値（meta）**

| キー | 値 | 使う所 | 復元したとき（機能設計書 7.2） |
|---|---|---|---|
| `lastExerciseId` | 最後に選んだ種目の ID | S-1 の初期表示、S-5 の初期表示 | 消す |
| `lastBackupAt` | 最後にバックアップを書き出した日時 | バックアップの案内、S-6 | 復元した時刻にする |
| `installHintDismissed` | ホーム画面への追加の案内を閉じたら true | 画面上部の案内 | 残す |
| `cardioSeeded` | 有酸素マシンを登録済みなら true | 起動時の初期データ登録（5.2） | 消して、もう一度登録する |

**読み書きの方法**
- ID は `crypto.randomUUID()` で作る（使えない環境では乱数から作る）。
- 日時は時差つきの ISO 8601 形式の文字列で保存する（例：`2026-10-12T19:42:05+09:00`）。「同じ日」の判定は端末の現地時刻で行う。
- 並び替えの一部（最後に記録した日時の比較、インデックス）は文字列の比較に頼っている。端末の時差が変わると前後関係が狂う可能性があるため、日本で使うことを前提とする（PRD「6」）。
- 1つの種目の記録は、`[exerciseId, performedAt]` インデックスでその種目の分だけを古い順に読む。前回記録や今日の記録は、読んだ後に `domain.js` で探す。
- 種目一覧の並び替え（最近記録した順）では、画面を開くたびに全記録を読む。個人利用の件数（数千件程度）なら問題にならないと考えている。遅くなったら、種目ごとの最終記録日時を保存する方式に見直す。

### 5.2 初期データ

起動のたびに次を確かめる（`main.js` の起動処理）。
- `muscles` が空なら、`seed.js` の筋肉リストを登録する。
- `meta` に `cardioSeeded` がなければ、`seed.js` の有酸素マシン3件のうち、同じ名前の種目がまだないものを登録し、`cardioSeeded` を true にする。筋トレの種目は登録しない（ユーザーが自分のジムのマシンを登録する）。

### 5.3 データ形式の変更（マイグレーション）

- 項目を足すだけで、古いデータにその項目がなくても既定値で扱える場合は、データベースのバージョンもバックアップの `schemaVersion` も上げない。
  - 例：種目の `kind`（ない場合は筋トレ）、筋肉の `hidden`（ない場合は表示）。v0.1.0 で作った種目に残っている `type` は使わない。
- 既存のデータを変換する必要がある場合は、次のようにする。
  - `DB_VERSION` を上げ、`onupgradeneeded` の中で古いデータを新しい形に変換する。古い版を開いたままのタブは、`onversionchange` で接続を閉じて移行を止めないようにしてある。
  - `SCHEMA_VERSION` を上げ、`parseBackup` で古い形式のファイルを新しい形に変換してから復元する。新しい形式のファイルを古い版で読み込もうとした場合は、「アプリを更新してから読み込んでください」と断る。

### 5.4 データ保全

| 対策 | 内容 |
|---|---|
| 永続化の要求 | 起動時に `navigator.storage.persist()` を呼ぶ。WebKit は、ホーム画面の Web アプリとして開かれているかどうかなどをもとに、この要求を許可するかを判断すると説明している（出典：WebKit Blog「Updates to Storage Policy」（2023-08-10） https://webkit.org/blog/14403/updates-to-storage-policy/ 、2026-10-13 参照） |
| ホーム画面への追加 | ホーム画面に追加した Web アプリは、Safari とは別に利用日数を数えるため、使い続けていれば、一定期間使わなかったことを理由にデータが削除されることはない、と WebKit が説明している（出典：WebKit Blog「Full Third-Party Cookie Blocking and More」（2020-03-24） https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/ 、2026-10-12 参照） |
| バックアップ | 上の2つでも、容量不足などで削除される可能性は残る（上の「Updates to Storage Policy」）。そのため、JSON の書き出しを促す（機能設計書「8. データ保全のための仕組み」） |

## 6. PWA の構成

### 6.1 manifest.webmanifest
- `display: "standalone"`（Safari のアドレスバーを出さない）
- `start_url: "./#/record"`
- 名前、アイコン、テーマ色

### 6.2 Service Worker（sw.js）
- インストール時に、`ASSETS` に並べたアプリ本体のファイル（HTML・CSS・JS・アイコン）をすべてキャッシュする。
  - ブラウザの HTTP キャッシュに残った古いファイルが入らないよう、サーバーから取り直す（`cache: 'reload'`）。
  - `ASSETS` のファイルが1つでも見つからないとインストール全体が失敗し、新しい版が入らない。ファイルを増やした・消したときは必ず `ASSETS` を直す。
- 読み込みは **キャッシュ優先**。オフラインでもすぐ起動できる。
- キャッシュ名にバージョン番号を入れる（`gym_log-<VERSION>`）。新しい版が有効になったら、古いキャッシュを削除する。
- 新しい版を検出したら、画面上部に「新しい版があります。［更新する］」と表示する。記録中に勝手に再読み込みしないため。押すと新しい版に切り替えて再読み込みする。
- Service Worker は HTTPS（または `localhost`）でしか動かない。GitHub Pages は HTTPS で配信される。
- 開発中に古いファイルがキャッシュから出ないよう、localhost では Service Worker を登録しない（試すときは URL に `?sw` をつけて開く）。

## 7. 画面描画とスタイル

### 7.1 表示（HTML）と処理（JS）の分け方

画面の構造は `views/*.html`（共通部分は `index.html`）に書き、`js/` には書かない。

| ファイル | 書くもの | 書かないもの |
|---|---|---|
| `views/record.html` など | 画面の構造（見出し、ボタン、入力欄）。一覧の1行分などの繰り返し部品は `<template>` で書く | `<script>`、`onclick` などの処理 |
| `js/views/record.js` など | データの取得、値の差し込み、ボタンを押したときの処理 | HTML の文字列（`innerHTML = '<div>…'` のような書き方） |

**画面の表示の流れ**
1. `main.js` が URL に対応する `views/<画面名>.html` を読み込み（`fetch`。毎回更新を確かめる）、`index.html` の入れ物に差し込む。
2. 対応する `js/views/<画面名>.js` の初期化関数を呼ぶ。
3. JS は `data-*` 属性で要素を探し、`textContent` などで値を入れる。一覧は `<template>` を複製して1行ずつ追加する。

```html
<!-- index.html（抜粋）：記録の行。記録・履歴・グラフ画面で共通 -->
<template data-tpl="set-row">
  <li>
    <button type="button" class="set-row">
      <span class="set-no" data-field="no"></span>
      <span class="set-main" data-field="summary"></span>
      <span class="badge" data-field="difficulty"></span>
      <span class="set-note" data-field="note"></span>
    </button>
  </li>
</template>
```

```js
// js/ui.js（抜粋）
const row = fill(tpl('set-row'), {          // <template> を複製し、data-field に文字を入れる
  no: setMark(no),                          // ①②③…
  summary: recordSummary(record, kind),     // 「60kg × 10回」「30分 ・ 8km/h」など（domain.js）
  difficulty: difficultyLabel(record.difficulty),
  note: record.note,
});
```

- 要素の探し方は `data-ref`（画面内で1つの要素）、`data-tpl`（テンプレート）、`data-field`（テンプレート内の差し込み先）にそろえる。class はスタイル専用にし、JS から要素を探すのには使わない。
- 値は `textContent` で入れる。備考などユーザーが入力した文字が HTML として解釈されないので、安全でもある。
- 例外：
  - グラフの SVG は数値から図形を計算する必要があるため、`chart.js` で組み立てる。
  - `main.js` は、読み込んだ `views/*.html`（自分のサイトのファイル）を `innerHTML` で差し込む。画面を表示できなかったときのエラー文の要素は JS で作る。
- `views/*.html` も Service Worker のキャッシュ対象にする（オフラインで表示できるように）。

### 7.2 スタイル

- 仮想 DOM などは使わない。
- 色は CSS 変数で定義し、iPhone のダークモードに合わせて切り替える（`prefers-color-scheme`）。辛さの5色もここで定義する。
- 主なボタンは、親指で押しやすい大きさ（目安として高さ 44px 以上）にする。記録画面では、記録ボタンがスクロールせずに見える位置に来るよう、入力欄を一覧より上に置く。
- iPhone の画面下端（ホームインジケーター）に隠れないよう、`env(safe-area-inset-bottom)` で余白を取る。
- 入力欄の文字は 16px 以上にする（iPhone で入力時に画面が拡大されないように）。

## 8. グラフ（chart.js）

- 外部ライブラリを使わず、SVG で折れ線・点・軸・目盛りを描く。
- 入力は `[{date, value}]` の配列だけにし、データ層とは切り離す（テストしやすく、後で差し替えやすい）。1日の値の計算（合計か最大か）は `domain.js` の `dailyValues` で行う。
- 点をタップすると、その日の記録を表示する（機能設計書 S-5）。

### 9.1 公開・更新の手順

**4つの番号と、上げるとき**

| 番号 | 場所 | 上げるとき |
|---|---|---|
| アプリの版 `APP_VERSION` | `js/domain.js` | 公開するたびに上げる（設定画面に表示）。機能を足したら真ん中（0.2.0 → 0.3.0）、直しだけなら右端（0.2.0 → 0.2.1） |
| キャッシュの番号 `VERSION` | `sw.js` | **ファイルを1つでも変えて公開するたびに必ず上げる**。上げないと、iPhone は古いファイルを使い続ける |
| データベースの版 `DB_VERSION` | `js/db.js` | 保存済みのデータを変換する必要があるときだけ（「5.3」） |
| バックアップ形式の版 `SCHEMA_VERSION` | `js/io.js` | バックアップの形式が古い版で読めなくなるときだけ（「5.3」） |

**手順**
1. ファイルを直す。ファイルを増やした・消したときは `sw.js` の `ASSETS` も直す。
2. Mac で単体テストと通しテストがすべて成功することを確かめる。
3. `APP_VERSION` と `VERSION` を上げる（必要なら `DB_VERSION`・`SCHEMA_VERSION` も）。設計書の「対応するアプリの版」と改訂履歴も直す。
4. git でコミットして push する。
5. iPhone でアプリを開き、「新しい版があります」→［更新する］を押す。設定画面の版が新しくなったことを確かめる。
6. 念のため、更新の前後でバックアップを書き出しておく。

### 9.2 公開されるファイル

- GitHub Pages では、リポジトリのファイルがすべて公開される（`tests/`・`tools/`・`docs/` も含む）。記録データはリポジトリに入らないので公開されない。
- `tests/e2e.html` を公開先で開くと、本番のデータにテスト用の記録が入ってしまう。これを防ぐため、`e2e.js` は `localhost`・`127.0.0.1` 以外では実行せず、理由を表示して止まる。
- 単体テスト（`tests/index.html`）はデータに触らないので、公開先で開いても問題ない。

## 10. セキュリティとプライバシー

- 外部のスクリプト、フォント、アクセス解析を読み込まない。
- `index.html` に Content-Security-Policy を `<meta>` で指定し、自分のサイト以外からの読み込みと送信を禁止する（`default-src 'self'; object-src 'none'; base-uri 'none'`）。
- 記録データは IndexedDB にだけ保存し、どこにも送信しない。
- GitHub に公開するのはアプリのコードだけ。書き出した CSV や JSON をリポジトリに入れないよう、`.gitignore` に `*.csv` と `gym_log_backup_*.json` を入れる。

## 11. 将来の拡張への備え

| 拡張 | 対応方法 |
|---|---|
| バーベルなどの種目 | 「筋トレ」の種目として登録するだけでよい。変更は不要 |
| 有酸素の種類を増やす（クロストレーナー、ローイングなど） | `domain.js` の `KINDS`・`KIND_FIELDS`（必要なら `CARDIO_FIELDS`）に足す。記録画面・グラフ・CSV はこの定義から作るので、ほかの変更は少ない。CSV に新しい列が要る場合は `io.js` も直す |
| インターバルタイマー | `views/record.js` に部品として追加する。データ層の変更は不要 |
| 推定 1RM、回数・総挙上量のグラフ | `domain.js` に計算関数を追加し、`graph.js` の項目の選択肢に加える |
| 複数端末での同期 | `db.js` の外側に同期処理を追加する。どこに保存するかは、プライバシー方針とあわせて別途検討する |
